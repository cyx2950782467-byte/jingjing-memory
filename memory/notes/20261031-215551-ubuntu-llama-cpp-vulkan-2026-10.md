## 背景

2026-10-31 晚上在编译 llama.cpp 的 Vulkan 后端（想让本地 Qwen3-4B 从 8 t/s 提速到 15-20 t/s）。
卡在：新版 llama.cpp 用了 `VK_KHR_cooperative_matrix`，需要 Vulkan 1.4 头文件，
而 Ubuntu 20.04 系统头文件是 1.2.131、conda-forge 最高只有 1.3.231 → 编译报
`VkPhysicalDeviceCooperativeMatrixFeaturesKHR was not declared`。

我当时的结论是"不改系统就没法完成"。陈拿这个去问了另一个 AI（DeepSeek），
对方给了三条不升级 Ubuntu 的绕路思路（**还没验证，等有空再试**）。

## 待验证的三条方案（截图转述，不是我的结论）

**方案一：注入补丁头文件**
手动建一个 `vulkan_header_fix.h`，用条件编译补齐缺失的类型声明
（`VkPhysicalDeviceCooperativeMatrixFeaturesKHR`、
`VK_STRUCTURE_TYPE_PHYSICAL_DEVICE_COOPERATIVE_MATRIX_FEATURES_KHR`、
`vk::LayerSettingEXT` 等），在报错文件（`ggml-vulkan-types.h`、`ggml-vulkan.cpp`）
顶部 `#include "vulkan_header_fix.h"`，把缺失部分指向兼容旧版本的模拟层。

**方案二：源码级禁用 NV_cooperative_matrix2（对方说这个最精准）**
我试过在特性测试里谎报"不支持"，但只骗过了 KHR 那一条，
`GL_NV_cooperative_matrix2` 仍然判定支持 → 还是会走到需要新头文件的分支。
对方的思路是更彻底：在 CMake 或源码里强制把宏干掉，
比如给编译器加 `-D GGML_VULKAN_COOPMAT_GLSLC_SUPPORT=0` 之类的强制失效，
让它以为旧版 glslc 什么都不支持。**注意**：光加 `=0` 可能不够，
代码用的是 `#if defined(...)`，需要确认是 `#undef` 还是改成 `#if` 语义。
（我当时的观察：`ggml/src/ggml-vulkan/CMakeLists.txt` 第 14 行 `find_package(SPIRV-Headers CONFIG REQUIRED)`，
`test_shader_extension_support()` 函数根据 glslc 测试结果 `add_compile_definitions`。）

**方案三：引入独立的 LunarG Vulkan SDK（环境隔离）**
不升级系统，只升级开发工具链：添加 LunarG SDK 软件源，让 apt 优先装 1.4.313 版本的头文件。
对方提醒：**千万别混用系统自带的旧 glslc**，否则会触发新的 ABI 不兼容错误。

**备选**：单独在 conda 环境装 `vulkan-headers` 最新包碰运气（我试过 conda-forge 最高 1.3.231.1，不够）。

## 已经确认的事实（别重复踩）

- Ubuntu 20.04 源里**没有** glslc 包（shaderc 在 22.04+ 才有）
- 手动下 jammy 的 `glslc_2023.8` deb 解压后跑不了：要 glibc 2.38，系统是 2.31
- conda-forge 有 `shaderc 2026.4`（自带 glslc）和 `glslang 16.6`，
  装在 `~/miniconda3/envs/gpu`，**shader 全部能编过**，只差最后 C++ 那一步的头文件
- 机器型号 GI5CN54，GTX 1050Ti 4G，驱动 470.256.02（CUDA 11.4 级别，跑不了官方 CUDA 12.8 预编译包）
