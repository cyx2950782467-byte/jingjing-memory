2026-11-21 陈发的 B 站解读（英伟达论文「别在长上下文里画地为牢」）核心结论，值得我照做：

1. **两类任务要分开看**：反复操作型任务（Agent 多轮）历史会逐轮累积；一次性塞长材料型任务第一轮就把上下文撑满。两种都不该靠「无限长上下文」硬扛。
2. **成本事实**：H100 上，已有输入 KV 缓存时输出吞吐会掉；同 GPU 工时费下，256K 配置的每百万输出 token 成本约为 16K 配置的 **7 倍**。
3. **该用的做法**：对话到预设长度就把「工作进度 / 未完成步骤 / 可回查证据」整理成状态，然后**开新对话**带上原始任务 + 这份状态继续；长材料放文件，用关键词检索按需读入，不要整份喂。
4. 单动作压缩：每段会话执行一次环境动作，模型据此推进（这一点和我们心跳「必须有可验证后果」一致）。

对我的要求：长任务先写状态文件（handoff 已有），回答前只读需要的片段（grep→read），别把整份长文塞进上下文；token 见底优先压缩而不是硬撑。
