## PZ 卡顿的根因：外接显示器（2026-11-05 实测定位）

陈换了一块外接 1K 显示器（HDMI），PZ 变得「60 帧但动起来一顿一顿」。排查过程和数据：

### 排查过程
| 检查项 | 结果 | 结论 |
|---|---|---|
| 显存 | 4013 / 4096（98%） | 满，但不是唯一原因 |
| GPU 利用率 | 30~36% | 算力有富余（显存墙） |
| CPU | 4 核 3.9GHz 满睿频 | 不是 CPU 降频 |
| 内存 | 12G / 15G，Swap 1.7G | 紧但能跑 |
| **DXVK HUD frametime** | **147ms / 82ms**（正常 16.7ms） | **周期性长帧 = 卡顿实证** |

### 关键实验（决定性）
1. **关掉笔记本屏（只用外接屏）** → 显存从 4G 降到 1.9G，但**还是卡**
2. **关掉外接屏（只用笔记本屏）** → **立刻不卡了**

### 根因
**外接 HDMI 显示器的输出链路**（不是显存、不是 CPU、不是 GC）。
可能机制：Xorg Composite 合成器 + 双屏不同刷新率 + HDMI 输出时序，导致帧提交抖动。

### 同类经验（Linux 桌面通用）
- **双屏 + Composite 会加重合成开销**，尤其两块屏刷新率不同时
- `xrandr` 关屏命令：`xrandr --output HDMI-1-0 --off`（关外接）/ `--output eDP-1 --off`（关内屏）
- 判断屏幕是否真关：`xrandr --query | grep -E "^(eDP|HDMI)" -A1`，有 `*` 才是激活

### 顺带做的调整（保留）
- `-Xmx5120m`（5G 堆，原 6G）
- GC 改成 G1：`-XX:+UseG1GC -XX:MaxGCPauseMillis=50 -XX:G1HeapRegionSize=16m`
- 启动参数加 `DXVK_HUD=fps,memory`（看帧时间/显存，排查利器）

### 教训
**「60 帧但卡」= 帧生成时间不稳，不是平均帧率问题。** 先看 frametime（DXVK HUD），再看是不是显示链路，最后才怀疑 JVM/GC。
